# 技术债与重构待办

本文基于 2026-07-23 的代码审查结果整理，目标是让后续维护和扩展有明确的实施顺序。清单描述当前实现，不代表需要一次性全部完成；优先级应结合数据规模、部署方式和实际故障再调整。

## 当前基线

- `npm run lint` 通过。
- `npm test` 通过：25 个测试文件，100 个测试通过，2 个测试跳过。
- `npm run build` 通过，生产构建产物约 73.5 kB CSS、多个按路由拆分的 JS chunk。
- `npm audit --omit=dev --audit-level=high` 和完整审计均报告 0 vulnerabilities。
- 当前项目已经有领域模型、共享数据归一化、SQLite/Redis 存储、Session、审计和安全响应头，后续应在这些边界上继续收敛，不再新增平行实现。

## 优先级定义

- **P0**：会造成数据错误、安全边界不一致或阻塞主要扩展，优先安排。
- **P1**：持续增加维护成本、发布风险或规模上限，建议近期安排。
- **P2**：体验、性能、运维和长期演进优化，可按业务需要安排。

## 待办清单

### TD-01 [P0] 统一存储 API 的业务编排与驱动适配

**当前状况**

- `server/core/apiCore.js` 和 `server/storage/redisApi.js` 各自实现登录、Session、媒体、管理员凭据、审计和公共数据读写路由。
- 同一个接口需要同时核对 SQLite、Redis、Vite 开发中间件、Node `server.js` 和 Vercel `api/storage.ts`；维护指南也明确要求逐入口核对。
- 共享的是部分工具和数据契约，路由分支、错误处理、限流位置和审计调用仍有重复，后续很容易出现“一个驱动已修复、另一个驱动遗漏”。

**优化后的结果**

- 把 HTTP 路由解析、鉴权、请求体限制、错误响应和审计编排收敛成一套 handler。
- SQLite、Redis 只实现统一的 `StorageDriver` 能力接口，媒体、Session、限流等差异封装在驱动内。
- Node、Vite、Vercel 只负责适配请求/响应对象和选择驱动；新增 MySQL 等驱动不再复制整套 API。

**验收标准**

- 同一组参数化契约测试同时跑 SQLite 和 Redis。
- 新增或修改端点只需要修改一处业务编排代码，并覆盖 Node、Vite、Vercel 入口测试。
- 两个驱动的状态码、错误字段、鉴权和审计行为一致，兼容入口有单独回归测试。

### TD-02 [P1] 明确公共数据的持久化模型和扩展上限

**当前状况**

- 站点设置、全部标签和全部卡片作为一个 `public_data` JSON 写入 SQLite/Redis KV；任何卡片变更都会重写整份文档。
- 服务端限制为最多 2000 张卡片、公共数据请求体 1 MiB，顶层 `updatedAt` 是整份文档的并发版本。
- SQLite 的并发语义依赖单进程同步读写，多实例或多进程不能获得 Redis 那样的原子版本比较。

**优化后的结果**

- 先确定规模门槛：若继续定位为个人站点，记录并监控当前上限；若需要多人编辑或更大数据量，迁移为卡片、标签、站点设置分表/集合的 Repository 模型。
- 使用数据库事务、实体级版本或明确的文档锁，避免不同卡片互相覆盖。
- API 支持分页、增量读取和按条件查询，数据 schema 迁移有版本号、迁移脚本和回滚说明。

**验收标准**

- 明确记录“继续 KV”与“迁移数据库”的触发指标。
- 并发编辑测试能区分不同卡片更新，不会静默覆盖。
- 数据迁移在备份副本上可重复执行，并有恢复演练记录。

### TD-03 [P1] 把媒体从 KV Base64 中剥离

**当前状况**

- SQLite 和 Redis 都把图片字节编码成 Base64 后存入 KV/JSON；单个媒体请求上限 10 MiB，Base64 还会放大内存、网络和 Redis 容量占用。
- 公共数据保存与媒体上传分两步执行，保存失败时可能产生孤立媒体，再依赖 Media GC 清理。
- 跨存储传输也是“先数据、后媒体”的非原子流程，中断时目标可能只有部分封面。

**优化后的结果**

- 使用文件系统、对象存储或专用 Blob 存储保存二进制，数据库/Redis 只保存媒体元数据、哈希和引用关系。
- 上传采用内容哈希或幂等 key，数据提交和引用更新有明确的状态机；失败任务可以重试或回收。
- GC 基于元数据索引和软删除窗口，跨存储传输有 manifest、断点续传和可恢复状态。

**验收标准**

- 图片不再进入 `public_data` 或 Redis JSON；大文件上传不会把进程内存一次性放大到多倍。
- 上传失败、保存冲突、传输中断和重复执行都有测试，且不会删除仍被引用的媒体。
- 旧媒体可以按批次迁移，迁移期间旧 URL 仍可读取。

### TD-04 [P1] 收紧服务端类型边界

**当前状况**

- 服务端核心主要是 `.js`（目录内约 37 个 JS 文件），`tsconfig.server.json` 只纳入 `server/**/*.ts`、`api/**/*.ts`，这些 JS 不在 TypeScript 类型检查范围内。
- `server/devMiddleware.ts` 的 Vite 请求和响应参数使用 `any`；ESLint 也显式关闭了 `@typescript-eslint/no-explicit-any`。
- `.d.ts` 和 JSDoc 需要手工维护，API handler 接收到的请求/响应对象没有统一类型。

**优化后的结果**

- 选择一条明确路线：将核心服务迁移为 TypeScript，或开启 `checkJs` 并补齐 JSDoc 类型；不再让两套类型系统长期并存。
- 为 Node、Vercel、Vite 三种请求/响应适配定义最小公共接口，驱动接口和 API DTO 使用同一来源的类型。
- 使用 `unknown`、类型守卫和错误类型替代业务代码中的 `any`，把类型检查纳入 CI 必过项。

**验收标准**

- `npm run typecheck:server` 覆盖所有服务端业务模块，而不是只覆盖入口 TS 文件。
- 新增驱动或端点缺少必需方法时能在编译阶段失败。
- `any` 只允许出现在第三方适配边界，并有局部说明和 lint 例外。

### TD-05 [P1] 拆分客户端存储服务与状态管理

**当前状况**

- `src/services/storageFactory.ts` 同时负责登录、Session、管理员凭据、公共/私有数据、驱动发现、跨存储传输、媒体 GC 和审计，还是一个可变的全局 singleton。
- 错误解析、`try/catch` 和返回结构分散在多个函数；`getStorage()` 可以在驱动尚未加载时返回默认的 SQLite 类型。
- 业务组件直接依赖这个聚合模块，后续增加 API 或离线能力会继续扩大耦合面。

**优化后的结果**

- 拆成 `authClient`、`publicDataClient`、`storageMaintenanceClient` 和统一 `apiClient`，驱动状态由一个只读 store 或 React context 管理。
- 驱动发现使用可复用的请求 Promise，失败状态显式暴露；页面不再把“尚未加载”误显示成 SQLite。
- API 错误统一为带 code/status/details 的类型，组件只处理业务结果，不重复解析 HTTP 响应。

**验收标准**

- 单个模块只覆盖一个 API 能力域。
- 驱动发现失败时有可见错误、重试和缓存降级策略，不会静默展示空数据。
- 客户端服务单元测试覆盖 401、409、429、5xx、网络断开和非法响应体。

### TD-06 [P1] 重构封面处理并清理遗留 WebDAV 逻辑

**当前状况**

- `src/services/coverAssetService.ts` 约 716 行，混合浏览器 Canvas 处理、远程图片代理、变体生成、上传、迁移和批处理进度。
- `_targetStorage`、`isStorageMediaUrl` 的存储参数等已成为无实际作用的遗留参数；`migrateCardCoversToStorage` 仍保留，但生产组件不再调用。
- `src/types.ts`、`server/sharedSecurity.js` 和测试中仍有 WebDAV 命名；封面服务有 2 个跳过测试，断言还指向旧的 `/api/webdav` 路径。

**优化后的结果**

- 拆成纯图片处理模块、媒体 API 客户端、封面迁移编排和失败报告模块。
- 明确“浏览器生成变体”和“服务端跨存储复制”的责任边界，删除无效参数；旧 WebDAV 代码要么完成迁移并恢复测试，要么经过数据审计和弃用周期后移除。
- 每个操作都有幂等行为、失败卡片列表和可恢复批处理。

**验收标准**

- 跳过的测试全部恢复、替换为当前 API 契约测试，或在文档中记录明确的删除决策。
- 上传、远程 URL、跨存储、变体补全和 GC 的核心路径不需要依赖完整 UI 才能测试。
- 同一张卡片重复执行优化不会无界产生孤立媒体。

### TD-07 [P1] 统一运行时中间件与配置校验

**当前状况**

- `server.js` 同时负责自定义 `.env` 解析、静态文件、压缩、ETag、限流、路由和驱动分发；Vite 与 Vercel 另有入口和 rewrite 配置。
- Node 入口有进程内限流，Redis handler 有 Redis 限流，开发态 SQLite 路径没有同等的限流层；策略分散在不同入口。
- `.env` 解析器是手写的，`PORT`、代理信任、存储驱动等配置缺少统一 schema 和启动时诊断。

**优化后的结果**

- 把配置加载/校验、静态资源服务、API middleware pipeline 和驱动路由拆成独立模块。
- 同源校验、请求体限制、限流、错误响应和安全头在所有运行时复用同一策略；差异只保留在平台适配层。
- 启动时一次性校验配置并输出不含秘密的诊断信息，提供 readiness 与 storage health 状态。

**验收标准**

- 开发、Node、Docker、Vercel 的关键 API 行为有集成测试矩阵。
- 非法端口、缺失 Redis URL、错误代理配置和生产 HTTP Cookie 配置能在启动或健康检查阶段明确失败。
- 限流策略写成配置/文档，分布式部署不会因为进程重启而完全丢失保护。

### TD-08 [P1] 建立真实浏览器流程测试和覆盖率门槛

**当前状况**

- 当前测试以领域、服务和 HTTP 合约单测为主，25 个测试文件没有覆盖真实浏览器路由、Cookie、懒加载、图片上传和生产静态服务器组合。
- 2 个封面迁移测试被跳过；没有覆盖率脚本或最低阈值。
- 关键保存流程存在“先上传媒体、再保存公共数据”的跨模块行为，单元测试难以发现页面集成回归。

**优化后的结果**

- 增加 Playwright 或同等工具的最小 E2E：公开首页/详情、管理员登录、保存冲突、封面上传、GC、旧路由和刷新恢复。
- 为 SQLite Node、Redis mock/测试实例和 Vercel handler 复用同一组 smoke case。
- 恢复或替换跳过测试，按风险为领域、API、媒体和关键 UI 流程设置覆盖率门槛。

**验收标准**

- PR 必须通过至少一条完整登录、编辑、刷新、重新读取流程。
- 失败的 E2E 能保留截图、网络日志或服务端日志，便于定位。
- 跳过测试数量为 0，或每个跳过项都有 issue、原因和到期时间。

### TD-09 [P2] 统一 API 契约、错误码和版本策略

**当前状况**

- API 通过 `?key=public_data` 和多个路径后缀组合表达能力，客户端接口、服务端 JSDoc 和测试分别维护 DTO。
- 错误主要依赖字符串，中文和英文并存；未提供可供客户端和外部工具消费的 OpenAPI/契约文档。
- 兼容入口 `/api/sqlite/*`、`/card/:id`、旧 `?tag=` 参数和 Vercel rewrite 依赖隐式约定。

**优化后的结果**

- 为 API 定义稳定的请求/响应 schema、错误 code、鉴权要求和弃用周期，必要时引入 `/api/v1`。
- 共享 schema 生成客户端类型、服务端校验和契约测试，减少手写 DTO。
- 兼容入口有访问统计或日志，达到迁移条件后再删除，不把历史路径永久混在主流程中。

**验收标准**

- 每个端点都有方法、状态码、请求体、响应体和错误 code 文档。
- 客户端不再根据自由文本判断错误类型。
- 兼容入口删除前有迁移说明和回归测试。

### TD-10 [P2] 补齐可观测性、备份和恢复演练

**当前状况**

- 服务端主要使用 `console.log`/`console.error`，缺少请求 ID、耗时、存储操作和失败原因的结构化记录。
- 审计日志记录业务动作，但不能替代 HTTP 错误率、媒体容量、GC 待处理数量和 Redis/SQLite 延迟指标。
- README 有备份步骤，但没有自动验证备份可恢复，也没有定期恢复演练记录。

**优化后的结果**

- 引入最小结构化 logger 和 request ID，记录状态码、耗时、驱动、操作类型，敏感字段默认脱敏。
- 健康检查区分进程存活、存储可用和数据可读；关键指标可被日志采集或监控系统消费。
- 备份、恢复、版本迁移和媒体 GC 有可重复脚本，并在 CI/定期任务中验证抽样恢复。

**验收标准**

- 能从一次请求日志串起入口、驱动操作和错误结果。
- Redis 不可用、SQLite 只读、备份损坏和恢复失败有明确告警信号。
- 至少保留一份最近恢复演练结果和操作记录。

### TD-11 [P2] 固定 Node 版本支持策略

**当前状况**

- `package.json` 允许 Node `>=20.19.0`，GitHub Actions 和 Docker 当前固定使用 Node 24；本地、CI、生产的支持范围没有明确说明。

**优化后的结果**

- 明确支持的 LTS 版本和升级窗口；CI 至少覆盖最低支持版本与当前生产版本，原生依赖 `better-sqlite3` 在矩阵中实际构建。
- Docker、README、`engines` 和 CI 使用同一版本策略，升级时有专门变更记录。

**验收标准**

- 最低支持 Node 版本上的 lint、测试、构建和容器启动均通过。
- Node 版本升级不依赖开发机缓存，`npm ci` 可重复完成。

## 建议实施顺序

1. 先做 TD-01、TD-04，建立统一驱动边界和可编译的服务端契约。
2. 再做 TD-05、TD-06、TD-08，降低客户端和封面业务的回归风险。
3. 根据实际数据规模决定 TD-02、TD-03；如果仍是单人、小数据量部署，可以先做迁移工具和指标，不必立即更换存储。
4. 最后推进 TD-07、TD-09、TD-10、TD-11，收敛运行时、发布和运维成本。

## 暂不列为缺陷的现状

- 当前 lint、单元/合约测试、构建和依赖审计均通过，不能把“已有测试不足”表述成当前已确认的功能故障。
- SQLite 与 Redis 的差异、`/api/sqlite` 兼容入口、Vercel rewrite 和整体 `public_data` 写入语义已经在维护指南中明确记录；在迁移方案落地前不应直接删除。
- 本清单不要求立即提交 Git commit 或删除遗留代码；删除 WebDAV/兼容入口前应先完成数据和访问使用情况核对。
